# 委譲の手引き（監督 LLM 向け）

監督（Opus など、知能の高い LLM）が、知能の高さを必要としない仕事を、ワーカー（Colab の Strata で動く Qwen3.8、DeepSeek Harness の headless）に任せるための手引き。
CLAUDE.md には短い版（[CLAUDE-snippet.md](CLAUDE-snippet.md)）だけを置き、詳細はこのファイルを読む。

## 1. 原則
- 任せるのは「知能の高い LLM がやらなくてよい仕事」。量が多い、繰り返しが多い、読む量が多い、何度も回す、のどれか。
- 監督は**ワーカーを待たない**。渡したら自分の仕事（設計、判断、ユーザーとのやりとり）を続け、終わった知らせで結果を見る。待つしかない仕事は任せない。
- ワーカーの「できました」は根拠にしない。根拠は、スクリプトが実行した検証と、監督が書いた受け入れテストの結果。
- 全部を任せるのも、全部を自分でやるのも失敗。台帳で偏りを点検する。

## 2. 任せるかどうかの判断（作業の前に毎回、上から順に）
1. **監督にしかできないか。** 設計・方針・トレードオフ、仕様の解釈、ユーザーとのやりとり、原因の分からない不具合の仮説立て、秘密・外部への送信・費用・取り返しのつかない操作 → 監督がやる。
2. **結果をすぐ使うか。** 次の判断がその結果しだい（クリティカルパス上）なら任せない。ワーカーは起動に約9分（止まっていれば）、1件に5〜10分かかる。急ぐ中くらいの仕事は、速いサービス（Sonnet / Haiku の下請けなど）に回す。
3. **渡せる形にできるか。** 3つとも満たすこと。
   - やることが決まっている（判断の余地が残っていない）
   - できたかを機械で判定できる（テスト、ビルド、check_report.py、差分の範囲）
   - 変更してよいファイル（または出力するファイル）を列挙できる
   満たさなければ、監督が判断を済ませて満たす形にするか、監督がやる。
4. **割に合うか。** 「カード + 受け入れテストを書く手間 + 結果を確かめる手間」が「自分でやる手間」の半分より小さいか。数行の修正、内容の決まった1ファイルの小さな変更は監督がやる。
5. 振り分けと理由（何番で決めたか）を台帳 `G:\local\delegation\ledger.md` に1行書いてから始める。

迷ったときの目安: **出力（または読む量）が、カードの10倍以上になるなら任せる。** カードと同じくらいの量なら自分でやる。

## 3. 任せる仕事の例
| 種類 | 例 | 判定のしかた |
|---|---|---|
| テストを厚くする | 監督が書いた本体に対する網羅的なテスト、境界値、異常系 | テストが通る + 受け入れテスト |
| 同じ形の繰り返し | 多数ファイルの置き換え、API の呼び方の移行、形式の変換、型注釈 | テスト・ビルド・grep |
| 読む量が多い調査 | 長いログ・ドキュメント・逆コンパイル結果を読み、要点と該当箇所を表にする | check_report.py（見出し・表・根拠の列） |
| 棚卸し・整理 | アセットの一覧と分類、未使用ファイルの洗い出し、文字列表の抽出 | check_report.py + 件数の照合 |
| 何度も回す | 数千回のテスト・ファズ・パラメータの総当たり、性能の測定 | 結果のファイルの形と件数 |
| 下書き | ドキュメント、コメント、変更履歴（事実は監督が渡す） | 見出しの有無 |

ゲームの移植作業での例（カードの例は [CARD-EXAMPLES.md](CARD-EXAMPLES.md)）:
- アセット（画像・音・データ）の一覧を作り、形式・大きさ・使っている場所で分類する。
- 逆コンパイルしたコードから、BGM・SE を鳴らす呼び出しを探し、「どの場面・どの条件で・どの音が鳴るか」を根拠（関数名・アドレス）付きの表にする。
- 文字列・メッセージの表を抽出して、移植先の形式に変換する。
結論（どう移植するか、どのアセットを作り直すか）は監督が決める。

## 4. 任せない仕事
- 設計、仕様が固まっていないもの、ユーザーに確かめないと決められないもの。
- 結果をすぐ使うもの（上の2）。
- 監督が書いたほうが速い、ほかとつなぐ部分（環境に依存する設定、数行の修正）。
- セキュリティ・並行処理の正しさなど、テストで捕まえにくく間違うと高くつくもの（任せる場合も、監督がコードを読む）。
- 2回差し戻しても通らないもの（監督が引き取る）。

## 5. 流れ
1. **カードを書く**（書式は [PROMPTS.md](PROMPTS.md) の「カードの雛形」）。判断はすべてカードの中で済ませる。曖昧な点は「決めてある」形に書く。
2. **受け入れテストを書く**（コードの仕事）。3〜8件、ワーカーが見落としそうな所だけを狙う。書いたら `delegate precheck` で落ち方を見る。調査の仕事なら、check_report.py の引数（見出し・表の列・最低行数・根拠）を検証コマンドに書く。
3. **渡す**: 1件なら `delegate run -Card <カード> -Async`、まとめてなら `queue\` にカードを置いて `delegate queue -Parallel 2`。続けて `delegate wait -Run <実行>` を run_in_background で動かし、終わった知らせを待たずに自分の仕事を続ける。
4. **確かめる**（終わったら）: `runs\<実行>\report.md` だけを読む。状態、範囲外の変更、検証と受け入れの結果、要確認がまとまっている。
   - ready_for_review: 差分のうち**テストの削除行**（ワーカーが前のテストを弱めていないか）と、受け入れテストが届かない部分だけを読む。調査なら、表の行を3つ選んで根拠を実際に確かめる。
   - verify_failed / accept_failed: 失敗の出力を見て、`followup` で差し戻す。
   - out_of_scope / no_change / worker_error / timeout: カードを見直す。
5. **決める**: `adopt`（採用・コミット）/ `followup -Note "<指示>"`（差し戻し）/ `discard`（破棄）。差し戻しは2回まで。3回目は監督が引き取る。
6. **要確認に答える**: ワーカーは決めずに要確認として返してくる。多くはカードの書き漏れ。差し戻すときは Note にまとめて答える（答えなかった項目は前回の判断のまま）。採用するなら、必要なものだけ次のカードに書く。

## 6. 受け入れテストの書き方
- 置き場: `G:\local\delegation\accept\<名前>\` の下に、対象リポジトリと同じフォルダ構成で置く（例: `accept\T-log-3\logstats\test_accept_status_class.py`）。カードに `受け入れテスト: T-log-3` と `受け入れコマンド: ...` を書く。
- ワーカーには見せない（カードの2項目はワーカーに渡す前に外される）。ワーカーが終わった後に作業ツリーへ置いて実行し、すぐ消す（コミットには入らない）。ファイル名はワーカーのファイルと重ならない名前（`test_accept_*.py` など）にする。
- 狙う所: 前回のレビューで見つかった種類の誤り、この環境の落とし穴（cp932 の出力、日本語と絵文字、CRLF、空行、エスケープ、境界の値、本物の時計での並行処理）、カードに書いた仕様の境界。
- 前提の操作（データを作る、サブコマンドを呼ぶ）も戻り値を確かめる。確かめないと、テスト自体の誤りが「ワーカーの誤り」に見え、差し戻しの指示まで誤る（T-inv-3 で実際に起きた）。
- 渡す前に `delegate precheck -Card <カード>` で、起点のコードに受け入れテストを一度流す。まだ無い機能のテストは落ちてよい。見るのは落ち方だけ（前提の操作の失敗、import の誤り、テストの書き間違いで落ちていないか）。出力は結果と理由の行だけに絞ってある。
- カードに書いていない仕様をテストしない（ワーカーが知りえないことで落とさない）。書き忘れに気付いたら、受け入れテストに入れるのではなくカード（差し戻しなら Note）に書く。

## 7. ワーカーについて知っておくこと
- Qwen3.8-Flash-Next IQ3_S（A100 40GB、256K）。コードは読みやすく、カードに忠実で、分からないことは要確認として返す。
- 見落としやすいもの: Windows の文字コード、現実のデータの乱れ、並行処理の順番。初期指示（worker.patch.yml）で注意させているが、受け入れテストで確かめる。
- 自分のテストは自分の想定どおりにしか書かない。ワーカーのテストが通っていることは品質の保証にならない。
- 同時に動かせるのは2〜3本（Colab のエンジンは1つ）。費用は Colab を動かしている時間で決まる（約 6.7 CU/時）。起動したら仕事をまとめて流し、終わったら止める（30分使われなければ自動で止まる）。

## 8. 振る舞いを保つ仕組み（要約の後に忘れないために）
過去の失敗: 委譲を続けた後、要約（コンテキストの圧縮）を境にルールを忘れて全部自分でやるようになった。指摘して CLAUDE.md に書くと、今度はつまらない修正も、本来自分でやるべき仕事も流し続けた。
- CLAUDE.md には短い判断ルールだけを置く（要約の後も読み込まれる）。詳細はこのファイル。
- 台帳に、振り分け・理由・結果が残る（delegate.ps1 が結果・採用・破棄を自動で書く）。要約の後も、何を任せていたかが分かる。
- 要約の直後と新しいセッションの最初に、このファイルと台帳の末尾20行と `delegate.ps1 status` を見る。
- 偏りの点検: 台帳の直近10件が全部どちらか一方なら、手を止めて理由を見直す。
- 委譲は delegate.ps1 経由だけにする。カードが無いと渡せないので、雑な丸投げが起きにくい。

## 9. コマンド
`G:\local\delegation\delegate.cmd` が PowerShell 7 で delegate.ps1 を呼ぶ（どのシェルからでも同じ書き方）。
```
delegate precheck -Card <カード>                         # 渡す前に、起点のコードで受け入れテストの落ち方を見る
delegate run -Card <カード> [-Repo <リポジトリ>] [-Async]   # 1件を渡す（-Async なら裏で、すぐ戻る）
delegate queue -Parallel 2                               # queue\ のカードをまとめて流す（queue\started\ へ移す）
delegate status [-Last 15]                               # 最近の実行の一覧と状態
delegate wait -Run <実行>                                 # 終わるまで待つ（Claude Code では run_in_background で）
delegate followup -Run <実行> -Note "<指示>" [-Async]      # 差し戻し（前回のブランチの上で。要確認と失敗を引き継ぐ）
delegate adopt -Run <実行> [-Message "<件名>"]              # 採用（squash merge + コミット + 後片付け）
delegate discard -Run <実行>                               # 破棄
```
- Claude Code の Bash ツール（Git Bash）から引用符つきの引数を渡すと `cmd //c` で崩れる。PowerShell ツールから呼ぶ。
- adopt は、差し戻しの元になった実行（前回の実行のブランチ）も片付ける（superseded.txt）。対象リポジトリに未コミットの変更があると断る。コミットには `Co-Authored-By`（`DELEGATE_COAUTHOR` で変える）と実行の記録の場所が入る。
- 裏の実行が途中で失敗すると、done.txt に `error: <理由>` が残り、status にもそのまま出る。
- `<実行>` は `runs\` の下のフォルダ名（`T-001-20261109-101500`）か、その先頭（`T-001`、最新のものが選ばれる）。
- pwsh は 7 以上（delegate.cmd が、Codex に同梱の pwsh、`C:\Program Files\PowerShell\7\pwsh.exe`、PATH の pwsh の順に探す）。
- worktree は `G:\delegate-runs\` の下（`DELEGATE_WT_ROOT` で変える）。dsh のサンドボックスは作業フォルダのアクセス権を書き換えるので、置き場には自分のフル コントロールが要る。初めて作るときに delegate.ps1 が付ける（自分で作ったフォルダを使うなら `icacls <置き場> /grant "<ユーザー名>:(OI)(CI)F"`）。ほかのアカウントからも読めるので、秘密を含むリポジトリには使わない。
- Strata が止まっていれば、delegate.ps1 が Colab Manager に起動を頼んで待つ（約9分）。

## 10. 状態の意味
| 状態 | 意味 | 次の操作 |
|---|---|---|
| ready_for_review | 範囲内・検証と受け入れテストが通った | report.md を見て adopt（必要な所だけ差分を読む） |
| accept_failed | ワーカーの検証は通ったが、受け入れテストに落ちた | 失敗の出力を見て followup（テストの中身は渡さず、直すべき点を言葉で） |
| verify_failed | カードの検証コマンドが通らない | followup（失敗の出力は自動で引き継がれる） |
| out_of_scope | 変更してよいファイル以外を変えた | カードの範囲が正しいか見直す。正しければ followup |
| no_change | 何も変えなかった | worker-report.md を読む（要確認で止まっていることが多い） |
| worker_error / timeout | ワーカーが異常終了・時間切れ | events.jsonl を見る。仕事を小さく分ける |
