# プロンプト集

## 1. ユーザーが監督に渡すプロンプト（セッションの始めに）

### 委譲を使って作業を進めてもらう
```
この作業を監督として進めてください。委譲の判断と手順は G:\local\delegation\docs\AGENT.md に従ってください。
- 判断・設計・レビューはあなたが行い、量の多い仕事・繰り返し・読む量の多い調査・何度も回す仕事は delegate.ps1 で Qwen3.8 に任せる。
- 任せたら待たずに、あなたは次の判断や設計を進める。
- 最初に、作業を分解して「自分がやるもの / 任せるもの / 理由」の表を見せてから始めてください。
作業: <やりたいこと>
対象: <リポジトリやフォルダ>
```

### 調査を任せてレポートにしてもらう（例: ゲームの移植）
```
<ゲーム名> の移植のために、<調べたいこと（例: BGM と SE が鳴るタイミング）> を調べたい。
逆コンパイル結果は <フォルダ> にある。調査は Qwen3.8 に任せ、レポートの形（見出し・表の列・根拠の書き方）と
受け入れの判定（check_report.py の引数）はあなたが決めてください。レポートは再利用できる形（表と根拠）で、
<出力先> に置く。結果は、根拠を数か所確かめたうえで要点だけ報告してください。
```

### 要約の後に振る舞いを戻す（ルールを忘れていそうなとき）
```
G:\local\delegation\docs\AGENT.md と、ledger.md の末尾20行と、delegate.ps1 status を見直して、
いま任せている仕事・任せるべきなのに自分でやっている仕事・自分でやるべきなのに任せている仕事を報告してください。
```

## 2. 監督が使う雛形

### カードの雛形
```
タスクID: <英数字と . _ ->
対象リポジトリ: <パス>
目的（なぜ）: <1〜2文。ワーカーが迷ったときの判断の拠り所になる>
入力（読むファイル・資料）: <パス>
出力: <調査・棚卸しの仕事なら出力するファイル。コードの仕事なら書かない>
変更してよいファイル: <パス（カンマ区切り）>
やること（判断の余地を残さない）:
- <決めてあることを全部書く。名前・型・例外・並び順・境界の扱い・出力の形>
- <曖昧になりそうな所は「〜のときは〜する」と決めて書く>
完了条件（コマンドで判定）: 検証コマンドと受け入れコマンドが成功する。
検証コマンド: <ワーカーにも見える検証。テストの実行、check_report.py など>
受け入れテスト: <accept\ の下のフォルダ名（コードの仕事）>
受け入れコマンド: <受け入れテストを実行するコマンド>
やってはいけないこと: <外部パッケージ、範囲外の変更、前のテストを弱める、など>
不明点が出たら: 決めずに「要確認」として返す
```
書く前の確認:
- 決めていないことが残っていないか（ワーカーは要確認として返してくるが、往復が1回増える）。
- 「どこまでやれば終わりか」がコマンドで判定できるか。
- 前回のレビューで見つかった種類の誤りを、受け入れテストか「やること」で押さえたか。

### 受け入れテストを書くときの観点
```
- カードに書いた仕様の境界（0、1、上限、空、最大、ちょうどの値）
- 現実のデータの乱れ（空行、欠けた項目、エスケープ、長すぎる行、未知の値）
- この環境の落とし穴（cp932 の出力、日本語と絵文字、CRLF、パスの空白と日本語）
- 並行処理（ロックの中で時刻や共有状態を読んでいるか。止まった偽の時計では確かめられない）
- エラーの出し方（トレースバックでなく "error: ..." と終了コード）
カードに書いていない仕様は確かめない。
前提の操作（データを作る、サブコマンドを呼ぶ）も戻り値を assert する。
書いたら delegate precheck -Card <カード> で、起点のコードでの落ち方を見る（まだ無い機能の不在で落ちるのは正しい）。
```

### 差し戻しの Note
```
<見つけた問題を、再現のしかたと期待する結果で書く。受け入れテストの中身は渡さない>
要確認への回答: 1 は <回答>。2 は <回答>。3 は前回のままでよい。
<追加の要望があれば、カードと同じ粒度で>
```

### レビューの手順（report.md を読んだ後）
```
1. 状態と範囲外の変更を見る。
2. テストの削除行を見る（awk で diff.patch から test ファイルの "-" 行だけ）: 前のテストが弱められていないか。
3. 受け入れテストが届かない部分（並行処理、セキュリティ、性能）だけコードを読む。
4. 調査なら表の行を3つ選んで、根拠（ファイル:行、関数、アドレス）を実際に開いて確かめる。
5. 採用 / 差し戻し / 破棄を決め、台帳に理由が残っていることを確かめる。
```

## 3. ワーカー（Qwen3.8）に渡るもの
- 初期指示: [worker.patch.yml](../worker.patch.yml)（dsh の system prompt の先頭を置き換える）。範囲の厳守、要確認の返し方、この環境の落とし穴、調査の根拠の書き方、報告の形。
- 本文: delegate.ps1 が組み立てる。カードから「受け入れテスト」「受け入れコマンド」を外したものに、次の前置きが付く。
```
次のタスクカードの作業を、このフォルダ（git の作業ツリー）の中で行ってください。
変更してよいファイル以外は変更しないこと。最後に、カードの検証コマンドを実行して結果を報告すること。
```
- 差し戻しでは、カードの末尾に「前回からの指示」（監督の Note、前回の検証の失敗、前回の要確認）が付く。
