# カードの例

実際に流したカードは `G:\local\delegation\cards\` と `queue\started\` にある（T-inv-*、T-log-*、T-rl-*、T-api-1）。
ここでは、ゲームの移植作業のように「知能の高い LLM でなくてよい調査・整理」の例を挙げる。パスや名前は例。

## 1. アセットの棚卸し
```
タスクID: G-assets-1
対象リポジトリ: G:\port\mygame
目的（なぜ）: 移植先で作り直すアセットと、そのまま使えるアセットを分けるために、全アセットの一覧が欲しい。
入力（読むファイル・資料）: extracted/ 以下すべて、src/ 以下のソース（参照の検索に使う）
出力: reports/assets.md
変更してよいファイル: reports/assets.md
やること（判断の余地を残さない）:
- extracted/ の下のファイルを1つずつ表の1行にする。見出しと列は次のとおり。
  # アセット一覧
  ## 概要
  （件数を種類別に。合計の大きさ）
  ## 一覧
  | パス | 種類 | 形式 | 大きさ（バイト） | 参照している場所 | 根拠 |
  - 種類は 画像 / 音楽 / 効果音 / フォント / マップ / データ / 不明 のどれか。拡張子とファイルの先頭のバイト（マジックナンバー）で決め、決めた理由を根拠に書く。
  - 参照している場所は、src/ を grep してファイル名（拡張子なし）が出てくる「ファイル:行」。無ければ「なし」。
  ## 参照されていないアセット
  （参照している場所が「なし」のもの）
  ## 要確認
- ファイルは変更しない。分からない形式は「不明」とし、先頭16バイトを16進で根拠に書く。
完了条件（コマンドで判定）: 検証コマンドが成功する。
検証コマンド:
- python G:\local\delegation\tools\check_report.py reports/assets.md --heading "# アセット一覧" --heading "## 一覧" --heading "## 参照されていないアセット" --table-columns "パス|種類|形式|大きさ（バイト）|参照している場所|根拠" --min-rows <ファイル数> --evidence
やってはいけないこと: reports/assets.md 以外を作ったり変えたりしない。
不明点が出たら: 決めずに「要確認」として返す
```
監督の確かめ方: `--min-rows` に実際のファイル数（`(Get-ChildItem extracted -Recurse -File).Count`）を入れて漏れを防ぐ。「不明」と「参照されていない」の行を数件開いて確かめる。

## 2. BGM・SE が鳴るタイミングの調査（逆コンパイル結果から）
```
タスクID: G-sound-1
対象リポジトリ: G:\port\mygame
目的（なぜ）: 移植先で同じ場面に同じ音を鳴らすために、どの場面・どの条件で・どの BGM / SE が鳴るかを、再利用できる表にする。
入力（読むファイル・資料）: decomp/ 以下（逆コンパイルした C）、reports/assets.md（音のファイルの一覧）
出力: reports/sound-triggers.md
変更してよいファイル: reports/sound-triggers.md
やること（判断の余地を残さない）:
- 音を鳴らす関数を探す: 名前に play / sound / bgm / se / music / sfx を含む関数と、それらを呼ぶ関数。見つけた「音を鳴らす関数」は最初の表に並べる。
- その関数を呼んでいる箇所を1つずつ、2つ目の表の1行にする。
  # 音のタイミング
  ## 音を鳴らす関数
  | 関数 | アドレス | 引数の意味 | 根拠 |
  ## 呼び出し箇所
  | 音（ID か名前） | 種類 | 場面 | 条件 | 呼び出し元 | 根拠 |
  - 種類は BGM / SE。場面は、呼び出し元の関数名と周りのコードから分かる範囲（例: タイトル画面、戦闘開始、メニュー決定）。分からなければ「不明」。
  - 条件は、その呼び出しを囲む if / switch を、変数名のまま書く（例: player_hp < 10）。
  - 音の ID が定数ならその値を書き、reports/assets.md の音のファイルと対応が分かれば名前も書く。
  - 根拠は「ファイル:行」と関数名。推測した場面には「（推測）」を付ける。
  ## 要確認
- コードは変更しない。
完了条件（コマンドで判定）: 検証コマンドが成功する。
検証コマンド:
- python G:\local\delegation\tools\check_report.py reports/sound-triggers.md --heading "# 音のタイミング" --heading "## 音を鳴らす関数" --heading "## 呼び出し箇所" --table-columns "音（ID か名前）|種類|場面|条件|呼び出し元|根拠" --min-rows 1 --evidence
やってはいけないこと: reports/sound-triggers.md 以外を作ったり変えたりしない。
不明点が出たら: 決めずに「要確認」として返す
```
監督の確かめ方: 呼び出し箇所の件数を自分で数える（`rg -c "<音の関数名>\(" decomp`）と表の行数を比べる。「（推測）」の行から3つ選んで根拠を開く。場面の解釈と移植の方針は監督が決める。

## 3. 何度も回す仕事（総当たり・繰り返しの測定）
```
タスクID: G-fuzz-1
対象リポジトリ: G:\port\mygame
目的（なぜ）: セーブデータの読み込みが壊れたデータで落ちないことを、たくさんの入力で確かめたい。
入力（読むファイル・資料）: src/save.py、tests/data/*.sav
出力: reports/fuzz-save.md
変更してよいファイル: tools/fuzz_save.py, reports/fuzz-save.md
やること（判断の余地を残さない）:
- tools/fuzz_save.py を書く: tests/data/*.sav を元に、1バイトの書き換え・切り詰め・ランダムな追加で入力を作り、src/save.py の load() に渡す。random.seed(1) から 5000 件。
- load() が ValueError 以外の例外を出した入力を、種類ごとに最初の3件だけ reports/fuzz-save.md の表に書く。
  | 例外 | 件数 | 入力の作り方 | 最初の入力（16進の先頭32バイト） | 発生箇所 |
- src/ は変更しない（直すのは監督が判断してから）。
完了条件（コマンドで判定）: 検証コマンドが成功する。
検証コマンド:
- python tools/fuzz_save.py --count 200
- python G:\local\delegation\tools\check_report.py reports/fuzz-save.md --table-columns "例外|件数|入力の作り方|最初の入力（16進の先頭32バイト）|発生箇所"
やってはいけないこと: src/ を変更しない。外部パッケージを使わない。
不明点が出たら: 決めずに「要確認」として返す
```
